# Деактивация объявлений

Краткое описание процесса деактивации объявлений при помощи **Django Q2** task queue, scheduler and worker. <br>
В качестве брокера будет использоваться существующая база данных (при помощи Django ORM).

## Механизм

Объявления деактивируются через два основных механизма:

1. **Планирование при активации:** При создании или обновлении статуса объявления на "активно" в админке или через API, планируется задача деактивации через `django-q2` на заданное время (по умолчанию 30 дней).
<br> *Задача пишется в отдельную таблицу, которая видна в админке (на самом дела, таблицу будет видно целых 4 штуки, но их видимость можно настаивать с помощью admin.py)*<br><br>

2. **Ежечасная пакетная деактивация:** Задача, запускаемая `django-q2` с указанным интервалом, деактивирует все объявления, срок которых истек. <br>*(Кажется, что это запасная функция, но пусть будет)*
___
## Функции
### Инициализация деактиваций при запуске сервера 
**`cleanapp` (management command):**
Следует запустить как минимум один раз, вызывает функции для деактивации устаревших объявлений и создает повторяющуюся задачу, выполняющую то же самое каждый час.
#### Вот оно, планирование задач: 
```realty.tasks.plan_mass_deactivation()``` Планирует задачу `realty.tasks.expire_all_outdated_realties` 
#### А вот и сама задача:
`realty.tasks.expire_all_outdated_realties()` Деактивирует все устаревшие объявления, которые соответствуют условиям: статус "активно", срок истек. **Выполняется либо при запуске management command либо каждый час воркерами/Q-Cluster**
___
### Индивидуальная деактивация объявлений 
*Запускается записью в таблице Django_Q_Schedule, <br>которая до этого была создана сигналом pre_save при Активации объявления<br>
По умолчанию эта запись создается на +30 суток вперед.*<br>
***Выполняется исключительно воркерами/Q-Cluster***

```realty.tasks.expire_realty(realty_id)``` 
- **Деактивирует (меняет статус объявления на "В Архиве")** одно объявление по `realty_id`, если оно соответствует условиям: не перевыставлялось заново, до сих пор имеет статус "активно", и срок действительно истек.
- **Обнуляет поле `published_at`**
- *Далее срабатывают сигналы на отправку Оповещений пользователю о переносе его объявления в Архив*
___


### Установка

Отдельная установка  `django-q2` не требуется, всё уже есть в `INSTALLED_APPS` и в `requirements.txt`, однако будет нужно выполнить миграции для создания таблиц задач:
   ```bash
   python manage.py migrate
   ```
## Запуск Django 
Должен состоять из трех частей:
```bash
# Запуск management command (хотя бы один раз за срок жизни базы): 
# - деактивирует expired объявления при своем запуске 
# - создаст или перезапишет задачу на такую деактивацию (будет выполняться ежечасно)
python manage.py cleanapp

# Запуск Django 
python manage.py runserver

# Запуск Q-CLUSTER - pool of workers that will handle your tasks
python manage.py qcluster
 ```
- Следует отметить, что если хотя бы один раз `cleanapp` будет запущена, задача для воркерам под названием `Mass Deactivation - HOURLY` окажется в базе данных, то до ее удаления, она будет исполняться в том случае, если с запуском сервера, будут запускаться и воркеры (qcluster)
- Рекомендуется при перезагрузке Django-сервера перезагружать и Q-CLUSTER
- Настройки - в разделе `Q_CLUSTER` в `settings.py`. <br> Первым делом можно перенастроить частоту обращения воркеров к Django за получением заданий - текущая настройка - `'poll': 1` - обращение выполняется каждую секунду*.  

### Важно

Для корректной работы деактивации объявлений их срок жизни выставлен в `constants.py` переменной `MAX_LISTING_DURATION`. По умолчанию срок – 30 суток.

____
> *Интересно, что, несмотря на частое (раз в секунду), обращение к базе за заданиями, с момента устаревания объявления до момента его деактивации по моим подсчетам проходит около 20 секунд. С такой малой точностью целесообразно перенастроить частоту `poll` на не чаще час раз в 60 секунд.
